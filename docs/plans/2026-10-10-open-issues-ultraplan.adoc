== Summary

. *#99 and #105 share one root cause.* This repo's `governance.yml` pins the reusable `governance-reusable.yml` at standards commit `84355587` (2026-08-27), 467 commits behind standards `main`. That commit predates two fixes: the self-supplied lock verifier and the split of the credentialed live-policy check. Both reds come from the old pin. The cure is a deliberate pin bump, not per-check edits.
. *A naive bump to standards HEAD is not safe today.* HEAD adds a strict UUIDv8 gate (`UUID v7 conformance`, ruling D320). It currently fails on *266* literals in this repo. 21 registered package UUIDs and the registry's own UUID need an owner decision. 208 are dependency bindings that the gate has no exemption for, which is a standards-side gap.
. *The minimal safe bump is `ed5e3f65`*, the commit that standards issue #993 names as the cure. It carries the fixes and predates the UUID gate. Two residual items remain: 7 floating `ref: main` checkouts inside that pin, and a live Actions-policy check that is advisory when no credential is supplied. Both need recorded determinations.
. *#99's Guix check is already green on `main`.* It needs a recorded "fixed on main" determination and no code change.
. *The live-policy check cannot be made fully blocking with the current secret model.* At `ed5e3f65` the live step exits with its own code when a credential is supplied, but exits 0 with a notice if the credential cannot read the Administration endpoint, and exits 0 with a notice when no credential is supplied. That is the "advisory" behaviour the owner has to accept or reject (D2).
. *#108 is closed and verified*, but its recurrence criterion is unmet. The lock gate is not a required check on `main`.
. *Binding-compliance debt is large and separate from these issues.* It includes 28 tracked retired `.a2ml` files, no `rsr-template-repo`-style `<repo>_chora.deed`, no `.k9.ncl` contracts, and a stale `copilot-instructions.md` that contradicts current bans. It should become its own track and must not be folded into the CI fix.

=== Why the linter fails (pinned reusable `84355587`)

At the pinned commit, the `workflow-lint` job runs `bash scripts/update-actions-lock.sh --verify-local` from the *caller's* repository root (lines 1127–1128 of that file). This repo does not ship that script, so the step exits 127. That is #105's first defect. Standards issue #930 describes the same class: the remedy text names a repo-relative path. At `ed5e3f65` the `workflow-lint` job no longer makes that call. The lock check moved to a separate `actions-lock-verify` job, which copies `check-actions-lock-gate.sh` and `update-actions-lock.sh` from standards (lines 1233–1296). The defect is therefore gone at both candidate pins.

=== Why the allowlist fails (pinned reusable `84355587`)

The `allowlist-preflight` job performs the live Actions-policy check with `GH_TOKEN: secrets.HYPATIA_SCAN_PAT`. This repo cannot read that secret, which I could not verify because the integration token is refused (HTTP 403 on the secrets and variables endpoints). The check therefore fails with an empty token. This is #105's second defect.

Each option is labelled. Where I depart from the most elegant long-term option, I say why.

[[d1]]
=== D1. Phase 1 pin target

* *A. `ed5e3f65`* (recommended for Phase 1). Fixes both reds, predates the UUID gate, and keeps the blast radius to two checks. Departs from the long-term default because it keeps 7 floating `ref: main` checkouts for now.

* *C. `f428562b`*. Newest pre-UUID pin. Equivalent to A for this repo, unverified beyond the simulation above.

[[d2]]
=== D2. Live Actions-policy check (#99 Allowlist half, #105 token half)

* *A. Provision `HYPATIA_SCAN_PAT`* as a repository secret: a token that can read the repository's Administration endpoints. Owner action only. Explicitly map `HYPATIA_SCAN_PAT: ${{ secrets.HYPATIA_SCAN_PAT }}` under `jobs.governance.secrets` in the caller workflow (`.github/workflows/governance.yml`). Only consider the live check evaluated after that mapping is present and a `main` run confirms the policy was read. It still exits 0 with a notice if the token cannot read Administration; that case remains not evaluated. This is the elegant target.
* *B. Accept as a documented exemption now* (recommended until A is done). Record in the repo: the reason, that the tree allowlist still runs and blocks, and a review date (suggest 2026-11-10). Also record in #99 that the live half is advisory by standards design, not silently passing.

Neither option is a silent pass. Neither should be a continue-on-error.

[[d3]]
=== D3. UUID scope under D320

* *A. Re-mint* the 21 registered package UUIDs and the registry UUID as UUIDv8, each re-registered at a patch bump as ADR-0002 did for the placeholders. Breaking for existing installs. Needs an ADR, and it does not auto-merge under the registry policy.
* *B. Keep them*, recording an owner ruling that a registry is not a package and that these identifiers are external or pre-D320 legacy. Needs the standards checker to carry that exception.
* *C. Defer the strict gate*: stay on `ed5e3f65` (Phase 1) and do not adopt HEAD until A or B is ruled.

Until D3 is decided, the strict UUID gate cannot go green for this repo, so HEAD (D1-B) cannot be adopted without a new, unexplained red.

[[d4]]
=== D4. Standards-side fixes (upstream issues)

Proposed for the owner to approve before anything is filed:

. `check-uuid-v8.sh` should exempt registry `Deps.toml` and `WeakDeps.toml` dependency bindings, matching its own `Project.toml` rule.
. The checker needs a documented way to type historical or legacy identifiers, so ADRs and changelogs are not forced to be edited.
. The rsr-template-repo's `governance` pin (`da2c748`) should be repointed to a pin containing `is_advisory_category` (standards #993 AC3).

These follow "solutions at source": fix the canonical gate, not this repo.

[[d5]]
=== D5. Recurrence control for #108 (lock drift)

* *A. Make the lock gate required on `main`*: add `governance / Actions lockfile verify` (or the Lock Sync Gate) to an active ruleset. This is the enforcing option, and it means a Dependabot bump cannot merge with a stale lock.
* *B. Confirm the estate `dependabot-lock-regen` App is installed on this repo*. `regen-dependabot-locks.sh` notes that the bump PR is otherwise merged anyway, so this is the only other path. Owner to confirm.

Either way, #108's acceptance criterion 4 ("record which") needs a recorded answer.

[[d6]]
=== D6. Format and signing tensions to rule on (not to act on)

* `.md` vs `.adoc`: standards `CLAUDE.md` lists `CHANGELOG.md`, `SECURITY.md` and `CODE_OF_CONDUCT.md` as GitHub-required Markdown. This repo and the template both ship `.adoc` versions (the template ships `CHANGELOG.adoc`). Which governs?
* `coordination.k9`: standards `AGENTS.adoc` names `coordination.k9` (first line `K9!`). The template ships `coordination.k9.ncl`. Which is canonical?
* Commit signing: standards says do not chase "Unverified"; template says "Always sign". Which applies to agent commits here?

= ADR 0002: Re-mint ten placeholder package UUIDs as UUIDv8 and re-register them
:toc: preamble

* Status: proposed (accepted when the BDFL merges the PR that carries it)
* Date: 2026-10-09
* Deciders: BDFL (Jonathan D.A. Jewell). Rulings of 2026-10-07 (estate
  UUIDv8, ruling D320), 2026-10-08 (re-mint and re-register the registered
  packages, at a patch bump, under ADR-008 profile T) and 2026-10-09
  (InvestigativeJournalist, SMTLib)

== Context

Ten of the 32 packages in `Registry.toml` were registered under UUIDs that
were typed by hand as placeholders, not drawn at random. They are runs of
consecutive hex digits, for example `d5f6a7b8-c9d0-4e1f-9a2b-3c4d5e6f7a8b`.
A census on 2026-10-07 counted the sequential-hex runs in every UUID in
the registry. The ten below scored 3 to 6. Every other entry scored 2 or
less. One of them, ShellIntegration's `c3d4e5f6-a7b8-4c9d-0e1f-…`, also
carries the variant nibble `0`. That is the reserved NCS variant, not the
RFC 9562 variant `10xx`.

A UUID is the join key every `Deps.toml` uses (`docs/REGISTRY-POLICY.adoc`
§ "Name / UUID immutability"). A placeholder is unique only as long as no
other template copies the same pattern. The estate's UUID standard is now
UUIDv8 (ADR-008 in `hyperpolymath/standards`, made strict by ruling D320).
On 2026-10-08 the owner ruled that the registered packages are not exempt
from that standard and must be re-minted and re-registered.

Policy has three rules that bear on this change:

* a UUID, once registered, is permanent;
* `Versions.toml` is additive-only;
* an edit to a UUID binding is treated as a removal plus a new
  registration, needs BDFL review and an ADR, and never auto-merges.

This ADR is that record.

One more package is affected without being a placeholder.
InvestigativeJournalist 0.1.0 (`379a7c0a-3675-4b32-b948-cb4760c6e442`)
declares dependencies on the old Causals and ZeroProb UUIDs.
`ci/validate.jl` Layer 2a keys `Registry.toml` by name. A `Deps.toml` that
binds `Causals` to its old UUID therefore fails once `Causals` is
rebound, and so would a second entry for the same name. The entry cannot
stay. Its upstream repository was also renamed to InvestigativeJournalism
(module included, upstream commit `98ccf6b`). Policy says a rename takes a
new UUID, so the package returns as a new registration.

== Decision

1. For each of the ten packages in the table below:
** remove the old UUID binding and every version registered under it;
** register the package again under a fresh UUIDv8 (ADR-008 profile T),
   with the same name and the same registry path;
** the new version is a patch bump of the last registered version. Each
   package repository bumped its own `Project.toml` in a merged PR.
2. Remove InvestigativeJournalist (`I/InvestigativeJournalist`, 0.1.0).
   Register InvestigativeJournalism 0.1.1 as a new package at
   `I/InvestigativeJournalism`, under a fresh UUIDv8.
3. Generate every new entry with RegistryTools v2.4.3, the library
   Registrator uses: `update_package_file`, `update_versions_file`,
   `check_deps!`, `update_deps_file`, `check_compat!` and
   `update_compat_file`. Generate it from the `Project.toml` at the
   registered commit, so `Deps.toml` and `Compat.toml` come out exactly as
   Registrator would write them. One input is filtered before generation
   because it cannot resolve: placeholder weak dependencies whose UUIDs
   name no package. SMTLib 0.2.1 declares nine, `11111111-1111-…` through
   `99999999-9999-…`, and they are left out of its `WeakDeps.toml`. A
   second guard drops compat entries for undeclared names. It fired for
   no package. Generation is idempotent: a second run over the result
   changes nothing.
4. The old versions are **removed, not carried over**. Their source trees
   declare the old UUID in their own `Project.toml`. Registering them under
   the new UUID would make the registry contradict the package source.
5. The deprecation trail is this ADR and the `CHANGELOG.adoc` entry. It
   cannot live in the old `Registry.toml` entries, which have to go: an old
   entry kept beside the new one would put two packages under one name.
   Layer 2a rejects that, and `pkg> add <name>` would become ambiguous.

== Alternatives considered

* *Exempt the registered packages and keep their UUIDs.* Rejected by the
  owner on 2026-10-08. The placeholders are exactly the identifiers that
  ruling D320 was made to retire.
* *Keep the old entries beside the new ones as a deprecation trail.*
  Rejected. Two entries would share one name, Layer 2a would fail, and
  `pkg> add <name>` would become ambiguous.
* *Re-register the same version numbers under the new UUIDs.* Rejected by
  the owner, who ruled a patch bump. One version number would otherwise
  name two different trees in this registry's history.
* *Keep the name InvestigativeJournalist.* Rejected. The upstream package
  and module are now InvestigativeJournalism, and a registry name must
  match the package's own `Project.toml`.

== Consequences

* **Existing installs break once.** A Manifest that pins an old UUID no
  longer resolves against this registry. The fix is `Pkg.rm` and then
  `Pkg.add` of the same name. InvestigativeJournalist users add
  `InvestigativeJournalism` instead.
* The two registered dependents move in this same change: LowLevel now
  depends on the new HardwareResilience and SiliconCore UUIDs, and
  InvestigativeJournalism on the new Causals and ZeroProb UUIDs. No registry
  metadata file (`Registry.toml` or any `*/*/*.toml`) references any of
  the eleven retired UUIDs any more. Only this ADR and the changelog name
  them.
* The removed versions remain recoverable from this repository's git
  history and from each package's own history. They are not installable
  from the registry.
* This merges only after each registered tree exists on its package's
  default branch. SMTLib's tree comes from `hyperpolymath/SMTLib.jl#48`,
  which fixes two load errors and the CI pin. InvestigativeJournalism's
  comes from `hyperpolymath/InvestigativeJournalism.jl#78`. If either
  squash commit's tree differs from the table, regenerate that entry
  first.
* Release tags (`v0.1.1`, `v0.2.1`, and `ViperPkg-v0.1.1` for the subdir
  package) are cut at the registered commits after this merges.
